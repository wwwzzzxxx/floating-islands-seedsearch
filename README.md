## 刷怪面积的口径：为什么从 68% 变成 97%

这是本次最重要的发现，值得单独一节。

### 问题

第一代结果里，我们说海底神殿"单人覆盖率最高 55%"、后来改口"68%"——两个数都不对，
因为**分母用错了**。我们一直按「4 座神殿的全部方块」当分母（4×58×58 = 13456），
但实际上**第 4 座神殿在最优挂机点上一块砖都贡献不了**。

穷举验证：排名前列的配对，「取最佳 3 座」的覆盖率和「4 座全算」的数字**完全相同**
（9184 = 9184、9838 = 9838）。所以第 4 座是摆设。

### 社区工具的口径

逆向 [SunnySlopes 的 MultiMonumentFinder-1.0.jar](https://www.bilibili.com/video/BV1bMbG64EXm) 确认：

| 证据 | 内容 |
|---|---|
| `messages_zh_CN.properties` | `最小可用面积必须是 6728~13455 之间的整数` —— 正是 2×58² 到 4×58² |
| `monumentFinderLibJ.dll` 常数 | 3364（=58²）、6728（=2×3364）、128、16384（=128²）、29 |
| 调用链 | `monumentSearch(..., pairLevel, biomeCheck, minGroupArea)`，`area = raw[i+5]` 由原生算出 |
| `getSelectedPairLevel` | 返回 `index+2`，即 **pairLevel 支持 2 / 3 / 4** |

**结论：面积定义和我们完全一致**（58×58 足迹的方块落入挂机点 128 格内的数量），
但他的工具可以只取 **3 座**——这就是数字对不上的原因。

截图里他设的是 `相连神殿数: 3`，分母是 3×3364 = 10092，9152 就是 **91%**；
我们同样的 9184 按 4 座算是 68%，按 3 座算就是 **91%**。**同一个数，口径差一倍。**

### 修正后的对比（同口径，绝对方块数可直接比）

| | 他的工具（pairLevel=3，扫 137 亿种子） | 本仓库（还额外要求四联小屋+村庄+河流+要塞） |
|---|---|---|
| 最高 | 9152 | **9838** |
| ≥9000 | 1 | **2** |
| ≥8500 | ~17 | **4** |

我们约束更多，结果还略好。

### 顺带发现：cubiomes 的 `getOptimalAfk` 会漏最优解

`quadbase.c` 的 `getOptimalAfk()` 是从 6 个候选点做洪水填充的**局部搜索**，
实测最多比全局最优差 **2026 格（约 15%）**。本仓库的 `triple2.c` 改用
「预计算偏移查表 + 穷举包围盒」，并用「直接数方块」在 200 个随机位置上验证过 0 偏差。

## 提速：四联结构的基是静态表，不用扫

（2026-10-11 补充。参考 [Cubitect/cubiomes-viewer](https://github.com/Cubitect/cubiomes-viewer) 源码，MIT）

深挖 Cubiomes Viewer 后发现的几件事，按价值排序：

### ① 四联小屋的全部基是预计算好的静态表

| 步骤 | 本仓库初版做法 | viewer 的做法 |
|---|---|---|
| 枚举四联小屋基 | RTX 4090 穷举 2⁴⁸，**740 秒** | 读 `rc/qh/` 预计算表（28 文件 / 差分编码 / 4.1 MB），**约 0 秒** |
| 四联神殿基 | 扫 2⁴⁸（半径放宽到 256） | `seedtables.h` 硬编码 **121 个**社区标准基，**0 秒** |

差分编码的读法（`src/searchthread.cpp` 的 `genQHBases()`）：

```
文件名           = 低 20 位（16 进制），即 (seed+salt)&0xfffff
文件每行         = 高 28 位的差分值
mid += 每行的值  →  s48 = (mid << 20) + low  →  push(s48 - salt)
```

**交叉验证**：把 viewer 的 `rc/qh/` 解码，得到 **755,745** 个基，与我们用 4090 穷举 2⁴⁸
得到的数量**完全一致**；本仓库 1483 个种子的小屋基 **1483/1483 全部命中**该表。
两条独立实现互相印证——既说明我们的扫描没写错，也说明那 740 秒是在重复造轮子。

### ② 临时查询用模逆，别遍历区域

`cubiomes/quadbase.c` 的 `scanForQuadBits()` 有个值得抄的技巧。要找「基的低 20 位等于
某给定值」的区域 `(i,j)`，而 `moveStructure(s48,-i,-j) = s48 - A·i - B·j`，于是

```
B·j ≡ s48 - A·i - lbit   (mod 2^20)
```

用 `B = 132897987541` 在 mod 2^20 下的**逆元**把 `j` 直接解出来，内层循环只走 `j += 2^20`。
把 O(宽×高) 的区域枚举降到近乎 O(宽)。自己写扫描器时可以直接把这个式子搬过去。

### ③ 便宜检查放在前面

viewer 的 `testTreeAt()` 分三趟：`PASS_FAST_48`（只做不依赖群系的便宜检查）→
`PASS_FULL_48`（加群系检查）→ `PASS_FULL_64`（完整 64 位测试）。
我们这条流水线本质上也是这个顺序（先结构位置、后群系/村庄/河流），只是没显式分层。

### ④ 耗时到底花在哪（消融法实测）

拿 2 万个 base、16 线程，用消融法量出来（`stage3.c` 顶部注释有完整记录）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 偏移扫描（169 次/基地的神殿四联位置判定） | **0.17 秒** | 0.001% |
| 变体循环（65536 个高 16 位变体的群系/村庄/河流验证） | **13.50 秒** | **99.98%** |

**"用四联结构筛种子"这一步本身几乎是免费的。** 耗时全在验证活下来的种子——因为
群系取决于完整 64 位种子，每个变体都要重新 `applySeed` + 采样群系，躲不掉。

顺着这个挖出两处冗余并已修（产出与原版逐字节一致，见 `stage3.c` 注释）：
四联结构判定只取决于种子**低 48 位**，而 `seed = base | (u<<48)` 的低 48 位恒为 `base`，
所以原版在 65536 个变体里反复算同一个值；4 个小屋的坐标同理。合计快约 16%
（15.9 秒 → 13.3 秒）。剩下的是 `applySeed` 与群系采样本身，属固有成本。

### 对复现的影响

- **想验证本仓库结果**：不必上 GPU。下载 cubiomes-viewer 的 `rc/qh/` 解码，几秒钟就能得到
  全部 755,745 个四联小屋基，然后直接跑 `stage3.c` 的变体搜索。
- **四联神殿**：社区标准基只有 121 个（`seedtables.h` 的 `g_qm_90`），可以直接取用。
  但注意本仓库用的是**放宽到 256 格**的标准（原因见「踩过的坑」第 1 条），
  放宽后的基不在那 121 个里——这一点两者不通用。

## 复现（给想自己扫的人）

依赖：[cubiomes](https://github.com/Cubitect/cubiomes)（结构位置与群系判定的权威实现）。
`stdbases.c` 另需 cubiomes-viewer 的 `src/seedtables.h`（121 个社区标准神殿基表）。

```bash
git clone https://github.com/Cubitect/cubiomes.git
# 注意：cubiomes 的 tests.c 也带 main()，不能整目录 glob，要显式列文件
CUB="biomes.c finders.c generator.c noise.c biomenoise.c quadbase.c util.c layers.c"
cd cubiomes
for f in pairs triple2 targeted stage3 stage4 coords near stdbases; do
  gcc -O3 -march=native -I. -o ../$f ../src/$f.c $CUB -lm -lpthread || echo "编译 $f 失败"
done
# 小屋基表（0.6 秒，替代 4090 上 740 秒的全空间穷举）
python ../src/decode_qh.py <cubiomes-viewer>/rc/qh -o hutbases.txt
```

六步流水线（全流程约 25 秒，16 线程）：

| 文件 | 作用 | 命令 |
|---|---|---|
| `src/decode_qh.py` | 从 cubiomes-viewer 预计算表解码全部 755,745 个四联小屋基，0.6 秒 | `python src/decode_qh.py <viewer>/rc/qh -o hutbases.txt` |
| `src/pairs.c` | 枚举每个小屋基在 ±N 偏移下的神殿四联，并用查表法算单人覆盖率，6 秒 | `./pairs 16 256 20` → `monpairs.txt` |
| `src/triple2.c` | 对每个配对算「4 座全算」与「取最佳 3 座」两种覆盖率，5 秒 | `./triple2 16` → `triple_out.txt` |
| `src/targeted.c` | 只对覆盖率排名前 N 的配对跑高 16 位变体搜索（群系/村庄/河流） | `./targeted monpairs_sorted.txt 60 -t 16 -out seeds.txt` |
| `src/stage4.c` | 要塞四联路口（含堡垒互斥过滤） | `./stage4 seeds.txt -range 4000 -out fort.txt` |
| `src/coords.c` | 输出某个种子的全部 tp 坐标 | `./coords <seed> <神殿偏移dx> <神殿偏移dz>` |

另有两个探索性工具：

| 文件 | 作用 |
|---|---|
| `src/near.c` | 限制神殿在原点半径 R 格内，找最佳 3 座组（用于回答"半径 1000 格能不能达标"） |
| `src/stdbases.c` | 评估"放弃四联小屋、改用 121 个社区标准神殿基"的可行性 |

关键取舍：**第 2 步的偏移范围直接决定覆盖率上限**。实测 ±6（约 3000 格）上限 7882，
±16（约 8000 格）到 9357，±20（约 1 万格）到 9838。要 8500 以上就必须把神殿放到一万格外。

## 踩过的坑（复现前必读）

1. **群系互斥（最隐蔽）**：`isQuadBase()` 只检查原点附近 4 个区域，小屋四联和神殿四联会被锚在**同一片 ~1024×1024 区域**里。
   而小屋要沼泽、神殿要海洋——两个群系要求在地理上互斥，184 万个变体全灭。
   **解法**：用 `moveStructure(base, -i, -j)` 把神殿四联的检查平移到别的区域（本例 ±6 区域 ≈ ±3 千米）。
2. **堡垒/要塞互斥**：1.18+ 两者同 salt、同 spacing，每区域位置相同、按群系二选一。
   分析要塞前必须 `applySeed(&g, DIM_NETHER, seed)` 后调 `isViableStructurePos(Fortress, ...)` 过滤，
   否则会把堡垒位置当成要塞（每个种子 ±4000 格内约一半区域是堡垒）。
3. **`Piece.pos` 随旋转变化**：竖向段取 (中x, 端z)、横向段取 (端x, 中z)，跨旋转比较必须用包围盒中心 `(bb0+bb1)/2`。
4. **距离比较**：`d2()` 返回的是**平方**距离，别和开方后的值比；方阵和共线要各用各的跟踪变量，否则会互相覆盖。
5. **「四联」在要塞里很常见**：BRIDGE_CROSSING 是 18×4 的走廊段，沿走廊天然按 19 格等距排列，
   所以「4 个路口成线/成方阵」几乎每个种子都有——这项不构成筛选条件，只是用来挑更好的。

## 数据包对扫描结果的影响（已实测）

- **群系分布、结构位置完全不受数据包影响**：数据包只改 `noise_settings` 的 `final_density`
  （把地形换成 `end_islands + base_3d_noise`，即末地那套），驱动群系的
  `temperature / vegetation / continents / erosion / depth / ridges` 全是原版引用。
  所以 cubiomes 按原版 1.18.2 扫出来的群系和结构坐标**全部有效**。
- **失效的是地形高度类指标**：低 Y 小屋、史莱姆农场（Y<40 无方块）这类依赖实际地形的标准，
  以及结构在浮岛上「落在岛上还是悬空」，只能进游戏验收。

## 游戏内验收状态

已在 1.18.2 + 数据包的实机世界验证过：

| 项目 | 状态 |
|---|---|
| 主世界结构坐标（小屋/神殿/村庄/河流） | ✅ 与原版放置算法一致，坐标直接有效 |
| 下界要塞坐标 | ✅ 已修正堡垒互斥 bug，每个坐标都用独立程序实证过（打印所属要塞起点、构件数、方阵四角） |
| 结构在浮岛地形上的落地形态 | ⚠️ 待逐种子验收（落在岛上 / 悬空 / 被岛屿切开） |
| **村庄是否落在主岛上** | ⚠️ **只能实测**——取决于数据包地形，`end_islands` 未移植前算不了 |

**实测揪出的两个 bug**：

1. 最早一版把 `-270 200 3758`（种子 4574346606646547320）报成要塞四联路口，
   实机 tp 过去是**猪灵堡垒**——原因是 1.18+ 堡垒与要塞同 salt、同 spacing，每区域按群系二选一，
   而当时的分析没做这个过滤。修复过程见「踩过的坑」第 2 条。
   这个种子修正后的要塞四联方阵在 `-572 200 34`（528 格）。
2. 第一代榜首种子 `6749578173375790244` 实机测得**村庄不在主岛上**（202 格外）。
   这是促成第二代重筛的直接原因——现在的 ①② 把村庄压到了 68 格。

**给验收者的提示**：tp 的 Y 统一给 200 再往下飞——浮岛世界下面是虚空，直接 tp 结构高度会摔下去。
